====================================================
L6: Task-Level Planning with PDDL
====================================================

Overview
--------

**Your GP1 tree runs the Task 1 steps in an order your team wrote down in
advance. This lecture lets a planner choose that order at run time.**

A **planner** is a program that takes a model of the world and a goal, and
searches for a sequence of actions that reaches the goal. The model is
written in **PDDL** (Planning Domain Definition Language), in two files. The
**domain** lists the kinds of objects, the facts that can be true or false
about them, and the actions, each with the facts it needs and the facts it
changes. The **problem** lists the objects in one situation, the facts true
at the start, and the goal.

The lecture starts with **classical planning**: states, actions, goals and
plans, and the assumptions behind them (full observation, deterministic
actions, a static world). None of the three holds in the ARIAC factory, so
your system plans again whenever ARIAC reports a fact that the problem got
wrong.

It then builds a PDDL domain for **ARIAC Task 1**, Steps 1b to 1e: eight
actions, from picking a cell off the conveyor to submitting the kit. Two
modeling mistakes, made on purpose, show that the planner uses every
shortcut the domain allows. Next comes a PDDL problem for one kit, first by
hand and then generated by a Python program from the factory state.

**Fast Downward** solves the problem, called from Python through the
**Unified Planning Framework (UPF)**. A satisficing search and an optimal
search are compared on a small and a large problem, and a **validator**
rejects a plan with two steps swapped.

The last part shows the limits of PDDL. Choosing four cells whose voltages
add up to the kit tolerance is arithmetic, and Fast Downward does not plan
with numbers. So GP3 makes that choice in a **selection step** written in
plain Python, and gives PDDL the result as goals. The lecture ends with the
growth in ground actions as the problem grows, and the GP3 pipeline, from
the factory state to a behavior tree.

.. important::

   **ARIAC tie-in.** Every example is ARIAC 2025 Task 1. inspection_robot_1
   picks cells off the inspection conveyor and places them on the two voltage
   testers. inspection_robot_2 places each tested cell in a slot of an AGV
   tray, or in the recycling bin if its voltage is out of range. The AGV then
   goes to shipping, and the kit is submitted.

Learning Objectives
-------------------

By the end of this lecture, you will be able to:

- Describe the assumptions of classical planning (full observation,
  deterministic actions, a static world) and name where each one does not
  hold in the ARIAC factory.
- Write a PDDL domain with types, predicates and parameterized actions with
  preconditions and effects for a part of ARIAC Task 1.
- Write a PDDL problem with objects, an initial state and a goal, and explain
  how a program generates it from the factory state.
- Run a planner (Fast Downward through the Unified Planning Framework) from
  Python and read the resulting plan.
- Check that a plan is valid against its domain and problem, and explain why
  a valid plan can still fail in the factory.
- Compute the voltage window left for the remaining cells of a kit, and
  explain why kit selection is done outside PDDL in GP3.
